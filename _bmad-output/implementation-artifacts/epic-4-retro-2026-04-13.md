## What went well

1. **The OTLP export foundation is proven end-to-end, not just theoretically correct.**  
   Every story validated its deliverables against the real OTel collector from both local dev and the Snowflake SP sandbox. Story 4.1 proved TLS transport and exporter lifecycle. Story 4.2 proved that real Snowflake Event Table data flows through the mappers to the collector and arrives in Splunk with correct attributes. Story 4.3 proved failure classification against real failure modes (invalid PEM, disabled gRPC port). The project now has empirical confidence in the entire export path.

2. **The integration test suite is a genuine project asset.**  
   Story 4.2 built a three-tier integration test infrastructure (foundation, collector, o11y) that validates the full path from Snowflake telemetry generation to Splunk Observability metric/trace visibility. This suite catches contract regressions that unit tests cannot, and the tier structure lets developers choose the cost/confidence trade-off per run. The 36 integration tests complement the 328 unit tests, giving the project comprehensive regression safety.

3. **The telemetry contract is grounded in real Snowflake Event Table data, not assumptions.**  
   Story 4.2 generated real telemetry using dedicated test stored procedures and UDFs, extracted real Event Table rows, and validated that the mapper output matched the architectural contract. This caught multiple real-world edge cases: ISO 8601 timestamp strings from `snow sql`, Snowflake uppercasing column aliases, UDF runtime lacking `snowflake.snowpark`, variable Event Table ingestion latency, and the `parent_span_id` location in `RECORD` vs `TRACE`. None of these would have been caught by unit tests with synthetic data alone.

4. **The code review process caught critical runtime issues in Story 4.1.**  
   The review identified that `_last_used` was only updated during `init_exporters()` (not on actual export activity) and that concurrent re-initialization could shut down an exporter while another thread was mid-export. Both were fixed with a condition-protected export reservation model and verified with a deterministic stress harness. Without the review, these would have been intermittent production failures.

5. **The collector signal routing was fixed as a side effect of thorough validation.**  
   Story 4.1's end-to-end validation discovered that traces and metrics were being duplicated to Splunk Enterprise (alongside logs) due to a misconfigured collector pipeline. The fix — removing `splunk_hec/splunk_enterprise` from the traces and metrics pipelines — is now documented and verified, preventing data pollution in future testing and production.

6. **Story records continued the richness standard from Epic 3.**  
   Each story record includes validated test IDs, detailed dev agent records, completion notes with specific debugging sequences, and explicit scoping of what the story does and does not implement. Story 4.2's 13 "Lessons Learned" entries and Story 4.1's "Snowflake SP Sandbox & gRPC Channel Lifecycle" research findings are especially valuable for Epic 5.

7. **The OTel SDK version compatibility was handled systematically.**  
   The difference between SDK 1.38.0 (Snowflake runtime) and 1.39.1 (local dev) — particularly `LogData` vs `ReadableLogRecord` and `LogExportResult` vs `LogRecordExportResult` — was identified early in Story 4.1 and handled with dynamic imports. This pattern carried cleanly through Stories 4.2 and 4.3 without introducing new version-sensitive issues.

## Friction and lessons

1. **The OTel Python SDK's public exporter surface hides gRPC status codes.**  
   The biggest design challenge in Story 4.3 was that `exporter.export()` returns only `SUCCESS` or `FAILURE` — the underlying `grpc.StatusCode` is caught and consumed inside the SDK's private `_export()` method. This means the wrapper usually cannot distinguish retryable from non-retryable failures. The resolution was pragmatic: classify bare `FAILURE` as terminal with `retryable=None` (honest uncertainty), and only populate `retryable` when a `grpc.RpcError` is directly surfaced to the wrapper. This is a fundamental SDK limitation that Epic 5 collectors must understand.

2. **Event Table ingestion latency is significantly more variable than documented.**  
   The story spec estimated 2–10 seconds for Event Table data availability. In practice, with accumulated telemetry from multiple test runs, data sometimes took 10–15 minutes to appear. The integration test timestamp assertions had to be relaxed from "within 5 minutes" to "after year 2020 and before now." This variability should be factored into Epic 5 integration test timeouts and Epic 7 freshness calculations.

3. **`snow sql --query` splits on semicolons at the CLI level, breaking Snowflake Scripting blocks.**  
   Multi-statement SQL with internal semicolons (like `BEGIN ... EXCEPTION ... END`) must use `snow sql --filename` instead. This was discovered during Story 4.2 integration test development and documented as Lesson 1 in that story. Epic 5 integration tests must follow the same pattern.

4. **Snowflake uppercases unquoted column aliases in `JSON_EXT` output.**  
   When using `snow sql --format JSON_EXT`, an alias like `AS trace_id` becomes `TRACE_ID` in the JSON response. The mapper constants expect lowercase names. Story 4.2 fixed this by lowercasing all keys except `RECORD_ATTRIBUTES` and `RESOURCE_ATTRIBUTES` during JSON parsing. This is a subtle gotcha for any future `snow sql`-based extraction.

5. **The dev collector configuration was not the source of truth — it drifted.**  
   The collector was silently sending traces and metrics to Splunk Enterprise via HEC, which was never the intended routing. This was only discovered because Story 4.1 performed end-to-end validation through to Splunk Enterprise and noticed unexpected trace/metric data in `index=otelcol`. Without that validation, the misconfiguration would have gone unnoticed and polluted the index during Epic 5 testing.

6. **UDF runtime does not have `snowflake.snowpark` — guard imports with `TYPE_CHECKING`.**  
   Story 4.2's test generators initially failed in UDF context because of a top-level `from snowflake.snowpark import Session` import. The fix: use `if TYPE_CHECKING:` guard. This is a Snowflake platform distinction (SPs have Snowpark, UDFs do not) that any module potentially used from both contexts must respect.

7. **Splunk Observability trace retrieval requires a two-step segment discovery workflow.**  
   The O11y APM API is not a simple `GET /trace/{id}`. You must first call `GET /v2/apm/trace/{traceId}/segments` to discover available segment timestamps, then `GET /v2/apm/trace/{traceId}/{segmentTimestamp}` to download a specific segment. Initial attempts to derive the segment timestamp from the collector span start time were inconsistent. This two-step pattern is now implemented in the integration fixtures.

## Breakthroughs worth keeping

1. **Module-level exporter singleton pattern with dual idle-timeout and keepalive defense.**  
   The gRPC channel lifecycle design — module-level exporter singletons protected by `threading.Lock`, gRPC keepalive pings to prevent NAT idle closure, and idle-timeout eviction as fallback — is the canonical pattern for any long-lived gRPC connection from a Snowflake stored procedure. The condition-protected export reservation model (added during code review) prevents the hot-swap race where re-init shuts down an exporter during an in-flight export.

2. **Three-tier integration test architecture with marker-based selection.**  
   The `integration_foundation` / `integration_collector` / `integration_o11y` marker tiers let developers run the fastest live slice for routine validation, the medium slice for collector verification, or the full slow suite for Splunk O11y eventual-consistency checks. This tiered approach scales to Epic 5 and beyond without forcing every test run to pay for O11y polling latency.

3. **Convention-transparent relay with minimal custom `snowflake.*` enrichment.**  
   The telemetry contract preserves all original `snow.*` attributes verbatim and adds only `snowflake.account.name` and `snowflake.record_type` as custom routing fields. No duplicate `snowflake.*` aliases for fields that already exist as `snow.*`. This clean separation makes the exported data immediately useful in Splunk without attribute confusion.

4. **`ExportOutcome` structured result with backward-compatible boolean truthiness.**  
   The `ExportOutcome` dataclass carries `success`, `terminal`, `error_code`, `error_message`, `signal_type`, `batch_size`, `retryable`, and `duration_ms` — all the context Epic 5 collectors need for health recording and operational logging. The `__bool__` method returns `self.success`, so existing `if export_spans(batch):` patterns continue to work unchanged.

5. **Dedicated telemetry test generators registered as app procedures.**  
   `generate_test_spans()`, `generate_test_logs()`, `generate_test_exception()`, and `generate_test_udf_telemetry()` produce controlled, verifiable telemetry with traceable `test_id` markers. These generators are reusable for Epic 5 integration testing and for any future regression testing that needs real Event Table data.

6. **OTel collector signal routing model documented and verified.**  
   The exact pipeline wiring (traces → O11y, metrics → O11y, logs → Splunk Enterprise) is documented with exporter counter evidence. This prevents future routing confusion and provides a reference for production collector configuration.

7. **Error message sanitization for Native App event safety.**  
   `_sanitize_error_message()` strips PEM blocks, URL credentials, and auth headers before recording error details in `_metrics.pipeline_health` or structured logs. This ensures NFR6 (zero credential exposure in logs/tables) is enforced at the export layer.

## Technical debt and carry-forward items

1. **Cursor rules still do not capture Epic 4 OTel/Snowpark patterns.**  
   The gRPC channel lifecycle findings (NAT idle timeout, keepalive, sandbox recycling), OTel SDK version compatibility (`LogData` vs `ReadableLogRecord`), `snow sql --filename` requirement for multi-statement SQL, Snowflake uppercasing of column aliases, and the public exporter's hidden gRPC status limitation are all documented in story records but not in cursor rules. New AI agent sessions will need to re-read story files rather than inheriting these as baseline knowledge.

2. **Integration tests depend on external infrastructure availability.**  
   The 36 integration tests require the dev OTel collector (`otelcol.israelcentral.cloudapp.azure.com:4317`), Splunk Enterprise (`eda.israelcentral.cloudapp.azure.com:8089`), and Splunk Observability Cloud API to be reachable. Network connectivity failures, firewall changes, or service restarts can cause false-negative test results. The tests are designed to poll with backoff, but extended outages will still cause failures.

3. **Event Table ingestion latency variability is not bounded.**  
   The 10–15 minute observed latency for accumulated runs exceeds what the integration tests originally assumed. The current tests handle this with relaxed timestamp assertions, but Epic 5 collectors that need freshness guarantees should not assume fast Event Table propagation.

4. **The `splunk-opentelemetry` package evaluation is captured but not formalized as a project decision.**  
   Story 4.1 evaluated and rejected the Splunk Distribution of OTel Python (2.8.0) because it's designed for long-running processes. This decision should be documented as a formal architecture decision record rather than buried in a story's dev notes, in case it's re-evaluated during post-MVP optimization.

5. **Warm-path exporter reuse was not observed from Snowflake SP sandbox.**  
   Story 4.1 validated that the module-level cache logic is correct, but consecutive `snow sql` calls each created a fresh Python sandbox. The warm-path optimization may only benefit triggered tasks that run repeatedly on the same warehouse node. Epic 5 should verify cache reuse behavior from real scheduled tasks.

6. **The dev collector HEC token is stored directly in the agent config file.**  
   Story 4.1 documented that the HEC token for Splunk Enterprise should be moved to an environment variable. This is a low-priority security hygiene item for the dev environment.

7. **`ACCOUNT_USAGE` pipeline mapping (CIM for HEC) is not yet implemented.**  
   The Epic 4 mappers cover Event Table signals only. Epic 5 Story 5.2 will need its own mapper for `ACCOUNT_USAGE` data, which follows a different schema and likely targets the OTLP log exporter with CIM-compatible field mapping for Splunk Enterprise.

## Epic 5 readiness

Epic 5 (**Incremental telemetry collection pipelines**) is the correct next step and does **not** require a fundamental replan. It builds directly on the export foundation and telemetry contract from Epic 4.

### What Epic 5 can build on safely

- **OTLP export module** (`otlp_export.py`) is proven end-to-end from both local and Snowflake SP runtimes. Exporters handle TLS, custom PEM, and gRPC keepalive.
- **Telemetry contract mappers** (`span_mapper.py`, `log_mapper.py`, `metric_mapper.py`) correctly transform pre-shaped DataFrames into OTel SDK objects with the full `db.*` / `snowflake.*` / `gen_ai.*` enrichment.
- **`ExportOutcome` structured results** from `export_result.py` give collectors everything needed for health recording and operational logging.
- **Pipeline telemetry helpers** (`pipeline_telemetry.py`) provide `record_batch_failure()`, `record_export_success()`, `log_terminal_failure()`, and `log_export_success()` — ready for collector invocation.
- **`_metrics.pipeline_health` table schema** is verified sufficient for `rows_failed` and `rows_exported` metrics.
- **Telemetry test generators** are registered and produce traceable Event Table data for integration testing.
- **Three-tier integration test infrastructure** can be extended for Epic 5 collector validation.
- **Manifest event definitions** enable provider-side operational log sharing.

### What needs attention before or during Epic 5

1. **Epic 5 collectors must own the Snowpark pushdown boundary.**  
   The Story 4.2 integration tests validated mappers using `snow sql` extraction (CLI subprocess), not Snowpark DataFrames. Epic 5 collectors must use Snowpark `session.sql(...).to_pandas_batches()` and verify that relational filtering stays in Snowflake while Python handles only batch serialization and OTLP construction. The integration suite should be extended to exercise the real Snowpark path.

2. **Stream management is new territory.**  
   Epic 4 had no stream interaction. Epic 5 Story 5.1 introduces `APPEND_ONLY` streams, stream advancement via zero-row INSERT into `_staging.stream_offset_log`, and transactional `BEGIN/COMMIT` around the read-advance cycle. These patterns need live validation against the dev account.

3. **Entity discrimination must be the first pushdown operation.**  
   The architecture specifies filtering on `RESOURCE_ATTRIBUTES:"snow.executable.type"` with the include list (`procedure`, `function`, `query`, `sql`) before any other processing. This is a Snowpark pushdown concern, not a mapper concern, so it belongs in the collector.

4. **`ACCOUNT_USAGE` collector needs its own mapper and watermark logic.**  
   Story 5.2 introduces watermark-based incremental collection with overlap windows, latency cutoffs, and dedup rules. The watermark table (`_internal.export_watermarks`) exists from Epic 1 but has never been written to. The `ACCOUNT_USAGE` data schema differs from Event Table schema and likely needs a separate mapper module.

5. **`sql_simplifier_enabled = True` must be set in collector procedures.**  
   The architecture requires this Snowpark session setting for performance. It should be one of the first operations in each collector procedure.

### What Epic 5 should NOT attempt

- No Streamlit UI changes. Collectors are backend stored procedures.
- No task provisioning or activation. That's Epic 6.
- No stale stream recovery or auto-suspend. That's Epic 7.
- No `_internal.config` schema changes. The config model is stable.
- No application-level retry loops. The OTel SDK's built-in retry is the MVP approach (V12).

## Key platform discoveries (Epic 4)

These discoveries should be encoded in cursor rules to prevent re-learning.

### 1. Snowflake SP sandbox and gRPC channel lifecycle

**Finding:** Module-level globals can survive across consecutive SP invocations on the same warehouse node (warm-start optimization), but Snowflake may recycle the sandbox at any time (scaling events, node rebalancing, memory pressure, warehouse suspend/resume). `atexit` handlers and daemon threads are NOT safe — Snowflake terminates SP processes with SIGKILL-like behavior. Handlers may be called from multiple threads concurrently, requiring `threading.Lock` on shared state.

**Impact:** Any module-level singleton pattern in a stored procedure must include a `if _instance is None` guard, use `threading.Lock` for thread safety, and design for correct behavior even if re-initialized on every call. `BatchSpanProcessor` is NOT safe for SP use — direct `exporter.export()` is the deterministic pattern.

**Reference:** Story 4.1 Dev Notes §"Snowflake SP Sandbox & gRPC Channel Lifecycle"

### 2. NAT gateway idle timeout and gRPC keepalive

**Finding:** Outbound SP traffic goes through Snowflake's NAT gateway, which closes idle TCP connections after 60–350 seconds. Snowflake's intermediate network infrastructure may not honor gRPC keepalive frames. The defense is dual: (a) gRPC keepalive pings at 30-second intervals as primary prevention, (b) idle-timeout eviction at 55 seconds as fallback. gRPC channels auto-reconnect with configurable exponential backoff after NAT closure.

**Impact:** All gRPC connections from stored procedures should use the `_CHANNEL_OPTIONS` tuple from `otlp_export.py`. The reconnect backoff values (100ms initial, 1000ms max) are tuned for short-lived SP windows.

**Reference:** Story 4.1 Dev Notes §5–6

### 3. OTel Python SDK public exporter hides gRPC status codes

**Finding:** `exporter.export()` returns only `SUCCESS` or `FAILURE`. The underlying `grpc.StatusCode` is caught inside the SDK's private `_export()` method. The wrapper usually cannot distinguish retryable from non-retryable failures. A `grpc.RpcError` may be surfaced to the wrapper as a secondary path, but this is not the common case.

**Impact:** Epic 5 collectors should treat bare `FAILURE` results as terminal with `retryable=None`. Only when a `grpc.RpcError` is directly surfaced can the failure be classified as retryable or non-retryable using the upstream retry set.

**Reference:** Story 4.3 Dev Notes §"OTel SDK gRPC Retry Behavior"

### 4. Event Table ingestion latency is variable (up to 15 minutes observed)

**Finding:** After calling a test generator procedure, telemetry data appeared in `SNOWFLAKE.TELEMETRY.EVENTS` within 2–15 minutes, depending on accumulated telemetry volume. The documented "few seconds" expectation is optimistic for heavy-traffic dev accounts.

**Impact:** Integration tests must poll with exponential backoff (not fixed sleep). Freshness calculations in Epic 7 should account for this variability.

**Reference:** Story 4.2 Lessons Learned §6

### 5. `snow sql --query` breaks multi-statement Snowflake Scripting

**Finding:** The `--query` flag splits on semicolons at the CLI level before sending to Snowflake, which breaks Snowflake Scripting blocks (`BEGIN ... EXCEPTION ... END`) that contain internal semicolons. The fix is `snow sql --filename` with a SQL file.

**Impact:** Any integration test or automation that needs multi-statement SQL in a single session must use `--filename`, not `--query`.

**Reference:** Story 4.2 Lessons Learned §1

### 6. Snowflake uppercases unquoted column aliases in `JSON_EXT` output

**Finding:** An alias like `AS trace_id` becomes `TRACE_ID` in `snow sql --format JSON_EXT` output. Mapper constants expect lowercase names. The fix is to lowercase all JSON keys in the extraction layer except `RECORD_ATTRIBUTES` and `RESOURCE_ATTRIBUTES`.

**Reference:** Story 4.2 Lessons Learned §3
